### A-1. なぜ「読み込めない」のに成功メッセージが出るか（PROVEN）

`extendSensorMasterFromEntries()`(index.html:3757-3781) の `added.push(room)` は、
実際に値を書けたかに関係なく **無条件で実行される**。そのため
`addedSensorRooms.length === 10` となり、取込結果画面には
「10件の部屋の感知器個数を追加しました。」（index.html:10417）と表示される。
利用者から見ると「成功と言われたのに個数が出ない」＝「読み込めない」になる。

### A-2. 補完値が保存されない（PROVEN・独立した別欠陥）

`extendSensorMasterFromEntries()` の永続化は `if (added.length) persistCurrentProperty();`
（index.html:3779）。「部屋は既に SENSOR_MASTER に在り、フィールド（total）だけを
補完した」ケースは `added.length === 0` になるため **保存が一度も呼ばれない**。
メモリ上は正しいが、再読込で補完した total が消える。

```
added（新規部屋）                    : []
DATA SENSOR_MASTER[1501]       : {...,"total":7,"totalSource":"②:fireflowIngest",...}
SAVE persistCurrentProperty 呼び出し : 0
```

### A-3. 2026-08-09 の修正が片側だけだった（根拠）

index.html:4795 のコメントは
「SENSOR_MASTER[room].total が監査で確認された INGEST_MAPPING_ERROR により破棄されていた問題を修正」
と記録し、描画側には「合計N」バッジまで実装済み（index.html:4801）。
しかし **破棄している当人である `sensorMasterFragmentFrom()`（fireflow_ingest 側）は未修正**。
LB側だけ直り、値の供給元が直っていないため、合計数のみ形式では今も0件になる。

### A-4. 実ファイルで確定が必要な分岐

- 「コスモザ・パークイースト1」の感知器数ファイルが
  **合計数のみ形式（丸数字①〜⑳）** なら FIRST_BREAK は上記 NORMALIZE で確定。
  - 傍証: `gridFormatParser.js`(bundle:196) は
    「コスモフォレスタ箕面/コスモザ・パークイースト1: 階ラベルが一切無い」と同じ系として並記し、
    コスモフォレスタ箕面は `totalOnlyGridFormatParser`（合計数のみ形式）の対応物件である。
- **位置依存2行形式（×N が2行）** なら Parser→NORMALIZE→DATA→RENDER は正常に通る
  （実行で確認済み: `{"state":"confirmed","sa":5,"tei":2,"total":7}`）。
  この場合の FIRST_BREAK は下記 A-5 に移る。
- 判別方法: そのファイルをアップロードしたときの取込結果画面の文言。
  「N件の部屋の感知器個数を追加しました。」が出るのに個数が出ない → NORMALIZE 破棄で確定。
  「認識できないフォーマットです」→ Parser 不一致（RAW で確定）。

### A-5. MASTER に部屋が無い場合（PROVEN・二次要因）

`toPropertyMasterIntake` の `payload.roomRoster` は **常に null**（感知器個数表からは部屋を作らない＝MASTER絶対ルール通り）。
実行で確認: `NORMALIZE roomRoster : null`。
したがって **FLOORS（MASTER）に該当部屋が無ければ、SENSOR_MASTER に値が入っても部屋カードが存在せず画面に一切出ない**。

```

DATA SENSOR_MASTER[1501]       : {...,"sa":5,"tei":2,"total":7}
RENDER 部屋カードが存在するか             : false
```

### B-1. FIRST_BREAK（最有力・要実ファイル確定）

**RAW段：`locateSensorBreakdownHeader()` による感知器内訳シートの未検出。**

- この関数はリテラル「差動式スポット型」「定温式スポット型」の同時存在を要求する。
- コスモザ・パーク（ス）イースト系の感知器帳票は
  「**差動/定温の語句・アイコンが一切無い**」ことが実データで確認済み
  （`positionalTwoLineFormatParser.js` ヘッダー、bundle:2512-2530。
  コスモザ・パークスイースト2 の実ファイルで確認）。
- 同系のフォーマットが点検結果報告書側の内訳シートでも使われていれば、
  `breakdownResult.entries` は空 → **①感知器内訳が未反映**、かつ
  `roomsFromSensorBreakdown` も空 → `自火報（一覧）` も無ければ
  **FLOORS が消火器設置場所テキストからの部分的な部屋一覧に落ちる**（index.html:9310）。
- これは 2026-08-09 に「66室→25件」として一度直した failure mode と同じで、
  修正がリテラル語句依存のため、語句を持たない帳票では再発する。

### B-2. 併発しうる別の break

- `差込データ` シート名が完全一致しない場合、物件名が
  **ハードコードの `コスモ宝塚シティフォルム`** になる（index.html:9182）。
  これは表示だけの問題ではなく、`currentPropertyScopeKey()` が `PROPERTY.name` から
  作られる（index.html:4320）ため、**新捺印表の保存スコープまでずれる**。
- `sheetToGrid()` は列オフセットのみ補正し **行オフセットは補正しない**（index.html:8895-8914）。
  シートの `!ref` が1行目から始まらない帳票では D7/K9/F6/D18 と
  総括表の固定行 10–16 / 26–35 が全てずれる。「一部だけ反映」の典型的な出方。

### C-2. DATA：MASTER に無い部屋は全て捨てられる（PROVEN）


### C-3. 画像圧縮を通さない（事実）

Legacy 経路は `compressImage()`（長辺1000px / JPEG 0.7、index.html:5574）を必ず通すが、
新捺印表経路は生のデータURLをそのまま送る（`routeUnifiedUpload` 6726）。

※ 新捺印表は密なグリッドのため 1000px へ縮小しないこと自体は精度上妥当。上限との関係の問題。

### C-4. 判別条件

- 画面に **エラー文** が出た → HTTP段（413 / 429 / 502）。文言でどれか一意に決まる。
- 「未対応（保存のみ）」または見た目上何も起きない → **C-1（HEIC/PDF 誤経路）**。
- 「捺印表を読み取りました（0部屋分…）」→ **C-2（MASTER不一致）**＝ B が真因。

## 4. 共通原因

**共通原因あり（ただし1つではなく2つ）。**

### 共通原因① MASTER（FLOORS）が正しく作られていない

- A: 感知器個数表は部屋を作らない（`roomRoster: null`）→ MASTER に無い部屋の値は画面に出ない。
- C: MASTER に無い部屋の捺印情報は `unmatchedRooms` として全捨て。
- B: その MASTER を作る唯一の経路が `parseExcelAndRebuild()` であり、そこが部分的にしか
  動いていない（B-1）。

→ **B が A と C の見え方を同時に壊す上流**である。3系統を1つにまとめる必要は無いが、
この依存関係は事実として存在する。

### 共通原因② 失敗が成功として表示される

- A: 値を1件も書けていないのに「N件の部屋の感知器個数を追加しました。」
- B: シートが見つからない項目はトースト1回で流れ、他項目は成功扱い
- C: 0部屋でも「捺印表を読み取りました」

「読めなかったことが利用者に伝わらない」という同一の設計欠落が3系統に共通している。

## 5. 修正優先順位

### P0

1. `sensorMasterFragmentFrom()`（fireflow-ingest.browser.js:2828）が RAW の `total` を破棄している問題。
   Parser が `total` を持っている場合はそれを採用する（sa+tei からの再計算は sa/tei が数値のときだけ）。
   ※ 本リポジトリには `public/fireflow_ingest/dist` のバンドルしか無い。**上流のソース側で直す必要がある**。
2. `extendSensorMasterFromEntries()` の永続化条件（index.html:3779）を、
   「新規部屋が増えたとき」ではなく「SENSOR_MASTER が実際に変化したとき」にする。
3. B-1 の確定。実ファイルを1つ手元に置き、内訳シートのヘッダー文言を確認する。
   語句非依存の検出が必要なら、`locateSensorBreakdownHeader()` のリテラル依存を一般化する
   （※原因確定後に着手。推測で直さない）。

### P1

4. C-1: `routeUnifiedUpload()` の分岐と `unifiedUploadInput` の `accept` を一致させる。
   HEIC を受けるなら新OCR経路へ、受けないなら accept から外す。
   PDF の新捺印表は新API の `mode:'bulk'` へ繋ぐ（実装済みで導線だけ無い）。
5. 失敗の可視化（共通原因②）。「追加しました」の件数を、
   実際に値が書けた件数に変える。0件なら成功文言を出さない。

### P2

6. `sheetToGrid()` の行オフセット未補正（index.html:8895）。
7. `parseExcelAndRebuild()` の物件名フォールバックが
   ハードコードの `コスモ宝塚シティフォルム` である点（index.html:9182）。
   物件名は StampStore のスコープキーでもあるため、誤った既定値は保存先まで汚す。
8. 新捺印表の 5.72MB 上限に対する事前案内（送信前にサイズを見て伝える）。

## 6. 最終判定

**PARTIAL_ROOT_CAUSE**

- **A（感知器個数）**: 合計数のみ形式での NORMALIZE 破棄を **実行で証明**（FIRST_BREAK確定）。
  ただし当該物件のファイルがその形式かどうかは実ファイル未入手のため未確定。
- **B（点検結果報告書）**: 中断ガードと固定位置依存・リテラル語句依存を洗い出し、
  最有力の FIRST_BREAK（内訳シート未検出 → FLOORS が消火器設置場所へフォールバック）を特定。
  確定には実ファイルが要る。
- **C（新捺印表）**: 「導線が繋がっていない」説は否定。
  代わりに HEIC/PDF が新OCR経路へ入らないこと、MASTER 不一致で全捨てになることを **実行で証明**。

3系統とも「最初に壊れる地点の候補」と「それを一意に決める判別条件」まで到達したが、
実ファイルが無いため A と B の最終確定はできていない。
