`applyStandardizedStampDataToLb()` が MASTER に無い部屋を落とすこと自体は
MASTER絶対ルール通りの正しい設計であり、欠陥は**上流のMASTERの側**にある。

### 前回仮説の判定

| 前回仮説 | 実ファイルでの判定 |
|---|---|
| C-1: HEIC/PDF が新OCR経路へ入らない | **今回は該当せず**（実ファイルは jpg で正しく新経路へ入る）。欠陥自体は残存 |
| C-3: 5.72MB上限（base64 8,000,000）に抵触 | **否定**。実ファイルは 0.59MB / base64 819,084 で余裕 |
| C-2: MASTER に無い部屋が全捨てされる | **成立（実測で確定）**。39室中24室 |

### ROOT_CAUSE

**B の MASTER 不備。C 自身の経路（入口の振り分け・API・サイズ上限・保存/復元）に破断は無い。**

### 影響範囲

新捺印表は全物件で「MASTERにある部屋しか反映されない」設計のため、
B が正しい部屋一覧を作れない物件では**必ず**同じ症状になる。

## 共通原因（実ファイルで証明されたものだけ）

### 共通原因① 部屋一覧（MASTER）の正本が無い帳票で、代用品へ黙って降格する

- B: 自火報（一覧）シートも部屋別内訳も無いため、**消火器の設置場所テキスト**へフォールバック
  → 70室（立入対象39戸のうち24戸が欠落）。
- A: 感知器個数表は仕様通り部屋を作らない（`roomRoster: null`）。
- C: MASTER に無い部屋は `unmatchedRooms` として全捨て → 24/39 が消える。

→ **B が A と C の見え方を同時に壊す上流である**ことが実測で確定した。

### 共通原因② 「読めていた値」を後段で捨てている

実ファイルで3箇所すべてを実測で確認した。

| 箇所 | 読めていた値 | 後段の結果 |
|---|---|---|
| A シート選択 | 3枚目に25室分の「差N・定M」 | 1枚目固定のため一度も読まれない |
| B 避難はしご | 設置場所テキストに19号室 | `extractLadderRooms()` → 0件 |
| C MASTER突合 | 実画像に39室 | 24室が破棄 |

### 共通原因③ 失敗・降格が成功として表示される

- B: 部屋一覧をフォールバックで作ったのに
  「『コスモザ・パークスイースト1』のデータを読み込みました（全70部屋、消火器78本、前回不良1件）」
  という**完全成功のトースト**が出る。降格した事実は伝わらない。
- C: 24室を捨てても「捺印表を読み取りました（15部屋分…）」。
- A は例外で、`unsupported` を正しく表示する（前回懸念した誤成功表示はこの物件では起きない）。

## 修正優先順位

「1物件だけ直す修正」ではなく、今後100物件に効く一般ルールとして書く。

### P0

**P0-1. MASTER の正本ソースを増やす（最も効果が大きい）**

`parseRoomRosterSheet()`（既存・実装済み）に `感知器数.xls` を通すと、
**3シートすべてで正確に39室を、階構成まで完全一致で取得できる**（実測）。

```
取得室数 : 39
階構成   : 15F[1512,1513,1514,1515,1516] 14F[1412..1416] 13F[1312..1316]
           12F[1212..1216] 11F[1112..1116] 10F[1012] 9F[912] 8F[803] 7F[703]
           6F[601,603] 5F[501,503] 4F[401,403] 3F[301,303] 2F[202,203]
=> applyPropertyMasterIntakeToLb() で LB の MASTER へ入る室数: 39
```

これは **Excel由来**であり MASTER絶対ルール（OCRからMASTERを作らない）に適合する。
現状は分類が `感知器個数表` になるため `parseSensorCountSheet` へだけ渡され、
既に成功する `parseRoomRosterSheet` が呼ばれていない。
→ **Excel系の資料は sensorCount と roomRoster の両方を解決し、
roomRoster が取れたら MASTER の正本候補として扱う。**

**P0-2. 入力シートの選択を「1枚目固定」から「値がある1枚」へ**

`index.html:10381`（感知器個数表）・`10450`（住戸一覧）の `SheetNames[0]` 固定をやめ、
全シートに Parser を試し `ok` になったものを採用する。
複数シート構成のExcel全般に効く一般修正。

**P0-3. sensorCount に「差N・定M」形式のParserを追加（9番目）**

`差<数字>・定<数字>`（`・` / `･` の表記ゆれ、全角数字、部屋番号セルの直下・同列）という
**一般ルール**として実装する。物件固有のハードコードにはしない。
2行形式（`positionalTwoLineFormat`）の兄弟として素直に並ぶ。

### P1

**P1-4. 部屋一覧をフォールバックで作った場合、成功として表示しない**

`roomsFromSensorData` が空で消火器設置場所へ降格したときは、
「消火器の設置場所から推定した部屋一覧です。実際の点検対象と一致するか確認してください」
を明示し、完全成功のトーストを出さない。共通原因③への直接対策。

**P1-5. `extractLadderRooms()` を「単純な号室列挙」にも対応させる**

階レンジ記法が無く `202、203、301、…号室` と並ぶだけの様式で0件になる。
テキストから号室を抽出し `newFloors` と突き合わせる既存の安全側ロジックは
そのまま使えるため、前段の記法判定を緩めるだけでよい。

**P1-6. 感知器内訳が警戒区域単位の帳票を、黙って0件にしない**

`locateSensorBreakdownHeader()` のリテラル依存を一般化しても、
警戒区域単位の帳票からは部屋別 sa/tei は作れない。
「この帳票は階単位のため部屋別内訳は取得できません。②感知器個数表が必要です」と
**取得不能を明示**する（推測で部屋へ按分しない）。

### P2

7. 点検年月日が K9（終了日）固定。`差込データ` は開始〜終了の期間（D9〜K9）を持つ。
8. `extractInspectionType()` が【機器】【総合】両方の場合を表現できない、
   かつ F6 を「前回の種別」とみなして反転する前提。この帳票では F6 は今回の種別欄。
9. `sensorMasterFragmentFrom()` の total 破棄（前回P0）。
   **本件では到達しないため格下げ**。合計数のみ形式の物件では依然として実在する潜在欠陥。
10. `sheetToGrid()` の行オフセット未補正。今回の実ファイルでは全シート `!ref` が
    1行目始まりのため顕在化しなかった。
11. C-1（HEIC/PDF が新OCR経路へ入らない）。今回のファイルは jpg のため該当せず。欠陥は残存。

## 最終判定

**ROOT_CAUSE_IDENTIFIED**

- **A**: FIRST_BREAK を実行結果で確定（RAW段のシート選択 + 未対応フォーマット）。
  前回のNORMALIZE仮説は**到達しない**ことを確認し、否定した。
- **B**: FIRST_BREAK を実行結果で確定（RAW段、部屋一覧の消火器設置場所フォールバック）。
  項目ごとに反映される/されないを実測で切り分け、正常な項目（物件名・点検者・消火器・
  前回不良・設備一覧）と破断項目（部屋一覧・感知器内訳・避難はしご）を分離した。
  前回のハードコード物件名仮説は**否定**した。
- **C**: FIRST_BREAK を実行結果で確定（MASTER突合で 39室中24室が破棄）。
  C自身の経路（入口・API・サイズ・保存/復元）に破断が無いことも確認した。
  **未確認は「この画像に対する実OCRの出力」1点のみ**であり、
  これは無人実行の禁止操作（実API課金）によるもので、原因確定を妨げていない。

3系統の関係も実測で確定した:

```
B（部屋一覧が消火器設置場所へ降格 → 立入39戸のうち24戸が欠落）
 ├─→ C の appliedRooms が 15/39 に減る
 └─→ A の値が入っても該当部屋カードが無い
A（1枚目固定 + 未対応フォーマット → 25室分の感知器個数が0件）
 └─→ B の帳票は警戒区域単位のため、感知器個数は最後まで表示されない
```

**次フェーズ（修正）へは進んでいない。ここで一度停止する。**
